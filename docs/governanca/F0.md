# F0 — barreira técnica entre código e produção

Escopo desta frente: CI com a suíte real, regras para o Claude Code, proteção
da `main` e Wait for CI na Railway. **Fora do escopo:** Brain, MCP, chave de
IA, bot do BotFather, Watch Paths, as funções `sonda-sessao-e50` e
`sonda-nav-e51`, e qualquer módulo de identidade, família, decisão,
publicação, convergência ou afiliação.

## 1. O que muda no repositório

| Arquivo | Papel |
|---|---|
| `.github/workflows/ci.yml` | CI: job `testes` em todo PR para a `main` e em todo commit da `main` |
| `scripts/testes.sh` | a suíte real (`tests/test_*.py` standalone); o mesmo comando no CI e localmente |
| `tests/test_uma_por_vez.py` | correção de teste instável (ver §5) |
| `CLAUDE.md` | regras de arquitetura e operação |
| `.claude/settings.json` | travas aplicadas pelo próprio Claude Code (ver §4) |
| `docs/governanca/ruleset-main-etapa1-sem-aprovacao.json` | ruleset importável da `main`, etapa 1 |
| `docs/governanca/ruleset-main-etapa2-com-aprovacao.json` | ruleset importável da `main`, etapa 2 |

Nenhum arquivo de runtime do worker muda.

## 2. Qual identidade cria os PRs do Claude (evidência)

| Ação | Identidade autenticada | Evidência |
|---|---|---|
| Abrir PR, revisar, comentar e mergear (ferramentas GitHub do Claude Code) | `leandrotpe123-lang`, a conta do dono (admin e **única** colaboradora) | `get_me` do conector; PRs #2, #3 e #4 com `user` e `merged_by` = `leandrotpe123-lang`; #3 e #4, com corpo gerado pelo Claude, foram criados **e mergeados em 4–8 s** |
| Push de branch | a credencial GitHub conectada pelo dono, anexada no servidor pelo proxy do Claude Code | documentação do Claude Code: "GitHub operations from the VM go through the GitHub proxy, which attaches the credential on the server side"; a das rotinas: "a rule that access can bypass doesn't block a run's push" |
| Autor e committer no git | só metadado: `Claude <noreply@anthropic.com>`; o GitHub exibe `@claude` porque esse e-mail pertence a essa conta | configuração git das sessões; `get_commit` |

**Conclusão: existe uma única identidade autenticada.** O Claude Code age no
GitHub **como o dono**, e o GitHub não consegue distinguir os dois. Daí:

- **aprovações ≥ 1** travam tudo: o GitHub não deixa ninguém aprovar o
  próprio PR e não existe segunda conta, nem para PR do dono;
- **aprovações = 0** deixam o Claude mergear o próprio PR, como já aconteceu
  com o #3 e o #4;
- "aprovação do push mais recente" também trava, porque quem fez o push é a
  mesma conta;
- lista de bypass não ajuda: o agente **é** o admin.

## 3. A barreira humana — decisão pendente do dono

| Opção | Como funciona | Força |
|---|---|---|
| **A. Conta de máquina para o Claude** (recomendada) | O Claude Code passa a agir como uma conta GitHub de máquina, com papel **Write**; o dono aprova com a conta pessoal; ruleset da etapa 2 (1 aprovação, aprovação do push mais recente, aprovação velha descartada, sem bypass) | **Real e aplicada pelo GitHub**: o agente não aprova o próprio PR, não mergeia sem aprovação, não altera ruleset (Write não pode) e não faz push na `main` |
| B. Etapa 1 provisória | PR obrigatório + CI obrigatório + sem force-push e sem exclusão, com 0 aprovações | barreira técnica contra código **quebrado** e contra push direto; **não é barreira humana**; o merge pelo agente fica bloqueado só pelo `.claude/settings.json` (defesa em profundidade) |
| C. Environment com revisor | deploy esperando aprovação num Environment do GitHub | fraca: quem aprova é a mesma conta; só segura enquanto as ferramentas do agente não tiverem "aprovar deployment"; e a `main` recebe código sem revisão |

Os termos do GitHub permitem **uma conta de máquina gratuita além da
pessoal**, usada exclusivamente para tarefas automatizadas.

Recomendação: ativar a **etapa 1 agora**, como ponte que já fecha push direto
e código quebrado, e migrar para a **opção A + etapa 2** como barreira humana
definitiva. **0 aprovações não é a decisão final**: é a única configuração
que funciona enquanto existir uma só identidade.

## 4. `.claude/settings.json` — o que é e o que não é

- Nega no Claude Code: merge e auto-merge de PR; as 36 ferramentas da
  Railway que **alteram** algo ou expõem segredo (`deploy`, `redeploy`,
  `update-service`, `set-variables`, `delete-*`, `railway-agent`,
  `list-variables` e outras); push explícito para a `main`; leitura de
  `.env` e arquivos de sessão. Ferramentas de **leitura** da Railway
  continuam liberadas para diagnóstico.
- Testado ao vivo: a sessão que escreveu o arquivo perdeu na hora o acesso às
  38 ferramentas negadas (o arquivo é recarregado imediatamente).
- Limites, por isso é defesa em profundidade e não a barreira final:
  - o mesmo recarregamento vale ao contrário: quem edita o arquivo remove a
    trava (`.claude/` é caminho protegido, mas rotinas rodam sem pedir
    permissão);
  - regra de Bash não é fronteira de segurança (variações do comando
    escapam); o push na `main` é barrado de verdade pelo ruleset;
  - os nomes valem para os conectores como aparecem nas sessões em nuvem
    (`mcp__github__…`, `mcp__Railway__…`); se o prefixo mudar, a lista
    precisa acompanhar.
- O conector da Railway é um caminho para a produção que **não passa** pelo
  GitHub. Para rotinas autônomas, a barreira forte é não incluí-lo.

## 5. CI — como foi validado

- Python 3.13 (mesma versão menor da produção) e `requirements.txt` de
  produção; actions fixadas por SHA de commit; token só leitura;
  `persist-credentials: false`.
- `compileall` do código de produção e depois `scripts/testes.sh`.
- Local, em 3.13.14: **3 rodadas seguidas, 28/28 arquivos verdes**, cerca de
  60 s cada.
- **Hermético**: 28/28 verdes num namespace sem rota e sem DNS (só
  loopback).
- **Mutações do gate, todas reprovadas**: teste falhando, arquivo com zero
  testes, teste travado (timeout), suíte encolhida (mínimo de 28 arquivos),
  exceção fora do harness e erro de sintaxe em módulo de produção.
- **Teste instável corrigido** — `test_uma_por_vez.py`, cenário `i`: comparava
  `id()` de dois objetos cujas vidas não se sobrepõem; o CPython reusa o
  endereço, os `id()` empatavam e o teste acusava "espera" inexistente
  (**83 falhas em 300 execuções** sob carga). Agora compara os objetos
  (`is not`): **300/300**. Contra um mecanismo que realmente espera, o
  cenário corrigido continua reprovando.
- **Estresse**: 28 arquivos × 10 execuções em paralelo, **280/280 verdes**.
- `actionlint` e `shellcheck` limpos.
- Concorrência: em PR, a execução nova cancela a anterior; na `main`, uma
  execução por commit, nunca cancelada (a Railway espera por ela).

## 6. Cliques do dono — nesta ordem

### Passo 0 — antes de o PR ser aberto: ambientes de PR da Railway

1. railway.com → projeto do bot → **Settings** (do projeto) → aba
   **Environments**.
2. Em **PR Environments**, confirme que **Enable PR Environments** está
   **desligado**. Se estiver ligado, desligue.

Motivo: com isso ligado, cada PR ganha um ambiente temporário com **todos os
serviços e variáveis copiados de produção** — um segundo worker com a mesma
`TELEGRAM_SESSION`.

Registro: em 06/10/2026 a opção estava **ligada**; o dono a desligou antes
de o PR da F0 ser aberto. Nenhuma ferramenta só-leitura da Railway expõe
essa chave do projeto: a conferência é visual, pelo dono.

### Passo 1 — revisar o PR da F0

Confira o diff e o check **`testes`** verde na aba **Checks**.

### Passo 2 — ruleset da `main`, etapa 1

**Importando o JSON** (computador):

1. Abra `docs/governanca/ruleset-main-etapa1-sem-aprovacao.json` na branch do
   PR → **Download raw file**.
2. GitHub → repositório → **Settings** → **Rules** → **Rulesets** →
   **New ruleset** ▾ → **Import a ruleset** → escolha o arquivo.
3. Confira na revisão: **Enforcement status = Active**; **Bypass list
   vazia** (não adicione "Repository admin"); alvo = **Default branch**.
4. **Create**.

**À mão** (celular ou sem o arquivo): **Settings** → **Rules** →
**Rulesets** → **New ruleset** ▾ → **New branch ruleset**:

- **Ruleset Name**: `main - protecao`
- **Enforcement status**: `Active`
- **Bypass list**: deixar vazia
- **Target branches** → **Add target** → **Include default branch**
- Marcar:
  - **Restrict deletions**
  - **Require a pull request before merging** → **Required approvals: 0**
    (etapa 1); marcar **Dismiss stale pull request approvals when new
    commits are pushed**; deixar desmarcados **Require review from Code
    Owners**, **Require approval of the most recent reviewable push** e
    **Require conversation resolution before merging**
  - **Require status checks to pass** → marcar **Require branches to be up
    to date before merging** → **Add checks** → digitar `testes` →
    selecionar o check com origem **GitHub Actions**
  - **Block force pushes**
- Deixar desmarcado todo o resto (em especial **Restrict updates**, que
  bloquearia até os merges, e **Require signed commits**).
- **Create**.

Verificação: no PR da F0, o check `testes` passa a aparecer como
**Required**.

### Passo 3 — merge do PR da F0

**Merge pull request**. Esse merge **reinicia o worker uma vez**: a Railway
implanta a `main` e o Wait for CI ainda não existe. O código de runtime é
idêntico, mas há a janela curta sem bot típica de serviço com volume. Faça
num horário de pouco movimento.

### Passo 4 — Wait for CI na Railway (depois do merge)

1. Se o GitHub pedir, aceite as permissões atualizadas do app da Railway:
   github.com/settings/installations → **Railway** → aceitar.
2. railway.com → projeto → serviço **worker** → **Settings** → seção
   **Source** → ligue **Wait for CI**.
3. O botão só aparece quando a `main` já tem um workflow com
   `on: push: branches: [main]`, ou seja, depois do Passo 3. Se não
   aparecer, aguarde alguns minutos e recarregue.
4. Se a Railway mostrar mudanças pendentes ("staged changes") para aplicar,
   aplicar pode reiniciar o worker mais uma vez (mesmo código).

Comportamento a partir daí: o deploy fica em `WAITING` até o CI do commit
terminar; CI falhou → deploy pulado; CI cancelado → deploy bloqueado; mais de
2 h → deploy pulado.

### Passo 5 — conferência

Me peça para verificar, somente leitura: `checkSuites` ligado no serviço, o
check `testes` como obrigatório num PR e o próximo deploy esperando o CI.

## 7. Etapa 2 — barreira humana real (quando o dono decidir)

1. Crie uma **conta de máquina** no GitHub (e-mail próprio, 2FA), usada só
   pelo Claude.
2. Como `leandrotpe123-lang`: repositório → **Settings** → **Collaborators**
   → **Add people** → conta de máquina → papel **Write** (nunca Maintain ou
   Admin).
3. Como a conta de máquina: aceite o convite.
4. Em claude.ai/connect-github, reconecte o GitHub autorizando **como a conta
   de máquina**. Isso vale para todas as suas sessões e rotinas do Claude
   Code. Se for pedido, instale o Claude GitHub App no repositório com a
   conta do dono.
5. Numa sessão nova, peça ao Claude para conferir a identidade (`get_me`) e
   abrir um PR de teste: o autor tem de ser a conta de máquina.
6. Troque o ruleset pela etapa 2: edite o existente (**Required approvals:
   1** e marque **Require approval of the most recent reviewable push**) ou
   importe `ruleset-main-etapa2-com-aprovacao.json` e apague o da etapa 1.
7. Rotina a partir daí: o Claude abre o PR → você revisa → **Approve** com a
   sua conta → merge. PR que toca `.github/`, `.claude/`, `CLAUDE.md`,
   `scripts/testes.sh` ou `docs/governanca/` pede revisão linha a linha.

## 8. Como desfazer

- **Ruleset**: Settings → Rules → Rulesets → o ruleset → **Enforcement
  status: Disabled** (ou excluir).
- **Wait for CI**: desligar o mesmo botão no serviço `worker`.
- **CI, `CLAUDE.md`, travas e teste**: PR revertendo o merge da F0.

## 9. Riscos conhecidos que ficam

- Até a etapa 2, não há barreira humana aplicada pelo GitHub (§2).
- Dependências sem versão fixa em `requirements.txt` (todas, menos
  `telethon`) são resolvidas de novo a cada build da Railway: todo deploy
  pode trazer versões novas. O CI instala igual e testa essas versões, mas
  fixar dependências é frente futura (mexe no worker).
- Exclusões e updates durante a janela de deploy podem se perder (limite já
  documentado em `pipeline/origem_apagada.py`).
